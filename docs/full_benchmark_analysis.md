## 1. 测试框架总览

### 1.1 测试维度

本报告覆盖 **两个互补的测试维度**：

| 维度 | 数据集 | 目标 | 指标 |
|------|--------|------|------|

## 5. 各系统问题总结

### 5.1 第三方系统的共性问题

```mermaid
graph LR
    A[第三方系统通用问题] --> B[代码质量低]
    A --> C[兼容性差]
    A --> D[可扩展性差]
    A --> E[文档过时]
    
    B --> B1[KGGen: 遮蔽内置函数 set()]
    B --> B2[TreeKG: 检查 JSON 类型]
    B --> B3[RAKG: O(n²) 相似度无法扩展]
    
    C --> C1[GraphRAG: 2.x→3.x CLI 全变]
    C --> C2[LightRAG: embedding_dim 写死 1024]
    C --> C3[AutoSchemaKG: 文件名硬匹配 .json]
    
    D --> D1[RAKG: 328 实体就 O(n²) 崩溃]
    D --> D2[LightRAG: 仅 2 跳子图]
```

### 5.2 具体问题清单

| 系统 | 问题 | 影响 |
|------|------|------|
| **KGGen** | `relations = set()` 遮蔽内置 `set()` | 运行时错误 |

| **TreeKG** | `data.get("entities")` 非 dict 崩溃 | 典型 JSON 健壮性问题 |
| **TreeKG** | TOC 标题占 26% 节点 | 知识噪声 |

## 7. Nanite 六大优化方向深度分析

> 本章六个方向基于当前基准测试暴露的短板，全部结合 Nanite 现有架构（BFS 级联管线、SysML v2 输出层、MCP 工具集）给出落地路径。

### 7.1 方向一：本体格式设计 — 用 SysML v2 本体约束 LLM 输出

#### 现状（Nanite 已有基础）

| 层级 | 现状 | 缺口 |
|------|------|------|
| **输出存储** | ✅ SysML v2 AST（PartDef/AttributeDef/RequirementDef/ItemDef + 20 种关系类型），`sysml_model.py` 强类型 | — |
| **提取阶段** | ❌ `EXTRACTION_CANDIDATES_PROMPT` 只做方向性引导，LLM 自由输出 JSON，MCP 层做类型映射 | 无 JSON Schema 强约束、无类型枚举校验 |
| **失败重试** | ✅ `KG_EXTRACTION_MAX_ITERATIONS`（默认 10）支持迭代重试 | 重试不感知 schema 错误 |
| **关系方向** | ✅ 20 类型中 `DIRECTIONAL` 集合（前端有） | 提取 prompt 未显式约束关系方向语义 |

#### 问题数据支撑

- CLUENER：**FP=644/1849（34.8%）** — 提取实体中 1/3 不在 GT 中
- Intel 手册：孤立实体 221（11.2%）— 类型映射失败的残留
- Laptop 文档：关系 277 条中大量为 auto-connect（allocation），语义类型模糊

#### 落地方案（结合 Nanite 架构）

```
提取 prompt (EXTRACTION_CANDIDATES_PROMPT)
  └─ 内嵌 JSON Schema: 实体类型 enum {PartDef, AttributeDef, RequirementDef, ItemDef}
                       关系类型 enum {20 种}
  └─ Ollama format=json + grammar 约束 (qwen3:8b 支持)
  └─ 输出后 pydantic schema 校验 (sysml_model.py 类直接复用为 schema)
      └─ 校验失败 → 带错误信息重试 (复用 max_iterations 机制)
  └─ 关系方向校验: DIRECTIONAL 集合中的类型强制单向语义
```

**关键点**：`sysml_model.py` 的 AST 类本身就是 schema 的单一事实源，不需要另建 schema 文件——用 pydantic 或 JSON Schema 生成器直接从 AST 派生。

#### 预期收益

| 指标 | 当前 | 目标 | 依据 |
|------|------|------|------|
| 精度 (CLUENER) | 0.652 | 0.70+ | FP 削减 30% 即可达成 |
| 类型误映射 | 未测 | 归零 | schema 枚举强制 |

#### 验证方式
- 同数据集重跑，对比 FP/精度变化
- 抽样 50 条 LLM 原始输出，统计 schema 违反率

### 7.2 方向二：实体与关系校准与消歧

#### 现状（Nanite 已有基础）

| 能力 | 现状 | 缺口 |
|------|------|------|
| 跨章节去重 | ✅ Phase 2（无 LLM，<1s） | 只做精确/近似字符串匹配 |
| 别名注册表 | ✅ `sysml_manager.py` 维护 | 别名仅来自 LLM 显式声明，无自动挖掘 |
| 实体合并 | ✅ `merge_entities`（别名转移+关系重定向+元数据合并） | 无自动触发机制，全靠 LLM 调用 |
| 前端可视化 | ✅ `web/kg_viz.html`（cytoscape.js） | 无人工校准编辑操作 |

#### 问题数据支撑

- **重复实体稀释 TP**：Nanite CLUENER 提取 1849 实体，若同义实体未合并（如 "ABS" vs "ABS系统" vs "方正ABS安全系统"），TP 被拆分、FP 虚高
- **孤立实体 11.2%**（Intel）：未连接任何关系的实体，部分是重复实体的残留
- **别名漂移**：跨章节同一概念不同写法（全称/缩写/英文/中文），substring 匹配无法覆盖

#### 落地方案

```
Phase 2 后新增校准流水线 (纯本地，无 LLM 或低成本 LLM):
  ① embedding 相似度聚类: nomic-embed-text 768d, 相似度 >0.92 → merge 候选
     (nomic-embed-text 已在工作站部署)
  ② 缩写-全称映射: 首字母缩写词典 + LLM 确认 (批量, 低温度)
  ③ 关系矛盾检测: A→B 与 B→A 并存 → 按类型优先级裁决方向
     (复用 web_server.py 的 TYPE_EDGE_PRIORITY 逻辑)
  ④ 前端人工校准: kg_viz.html 增加 merge/split 操作按钮
     (MCP 工具 sysml_merge_entities 已存在, 直接暴露)
```

**关键点**：校准必须**无 LLM 或批量 LLM**——Phase 2 现在 <1s 的优势不能丢。embedding 聚类是本地方案（nomic-embed-text 已部署）。

#### 预期收益

| 指标 | 当前 | 目标 | 依据 |
|------|------|------|------|
| FN (CLUENER) | 976 | -10% | 同义实体合并后 TP 回升 |
| 孤立实体占比 | 11.2% | <5% | 重复残留回收 |
| 关系矛盾对 | 未测 | 归零 | 方向裁决 |

#### 验证方式
- 合并前后 TP/FN 对比（同数据集两次运行）
- 孤立实体数量统计对比

### 7.3 方向三：领域 RAG 增强实体抽取

#### 现状（Nanite 已有基础）

| 能力 | 现状 | 缺口 |
|------|------|------|
| 实体传播 (Phase 2) | 全文 substring 匹配（大小写不敏感） | 无语义检索，别名漂移时传播失败 |
| 级联提取 (Phase 3) | 每 5 段盲提取 | 无相关上下文注入 |
| 向量存储 | ✅ RAG 引擎已有（bge-m3/nomic-embed-text） | 未接入 KG 构建管线 |

#### 问题数据支撑

- CLUENER 召回 0.552 — 41.5% GT 实体未被提取
- RESUME 召回 0.368 — 最弱项（与 RAKG 0.397 差距最大）
- 长文档（Intel 5342 页）传播队列稀疏，级联易中断

#### 落地方案

```
Phase 2 实体传播升级:
  ① 向量检索: 新实体 embedding → 在未处理章节中检索 top-k 相关片段
     (替代纯 substring, 召回语义同义表述)
  ② 上下文注入: 提取时携带 [焦点实体所在段落 + 邻接实体列表] 作为 few-shot 锚点
  ③ 术语表: 已建 KG 高频实体 (freq>N) 作为领域词典注入 prompt
  ④ Grounding 验证: 新实体必须能在 source_sections 找到支撑文本
     (source_sections 字段已存在, 强化校验)
```

**关键点**：这是对现有 Phase 2→3 传播机制的增强，**不是新管线**。向量检索复用 `rag/` 模块。

#### 预期收益

| 指标 | 当前 | 目标 | 依据 |
|------|------|------|------|
| 召回 (CLUENER) | 0.552 | 0.60+ | 语义传播覆盖漏网实体 |
| 召回 (RESUME) | 0.368 | 0.42+ | 术语表+上下文注入 |

#### 验证方式
- 传播队列覆盖度：新方案 vs 旧方案的 (实体, 章节) 配对数量
- 同数据集召回对比

### 7.4 方向四：隐含关系推理

#### 现状（Nanite 已有基础）

| 能力 | 现状 | 缺口 |
|------|------|------|
| 关系提取 | 显式提取（20 种类型） | 无推理闭包 |
| 连通性保障 | auto-connect（新实体→焦点实体 allocation） | ⚠️ 产生大量低质量双向关系（历史教训：移除 _connect_global_orphans 就是为抑制虚假关系） |
| 关系去重 | 前端 TYPE_EDGE_PRIORITY 裁决 | 只在前端，不修正数据 |

#### 问题数据支撑

- Intel 手册：10443 关系 / 2294 实体 = **4.6 关系/实体**，密度偏高，auto-connect 贡献显著
- 关系方向混乱：双向关系常见（无向语义被建为两条有向边）

#### 落地方案

```
关系后处理流水线 (Phase 4 聚合后):
  ① 规则闭包 (零成本):
     - Containment/Composition/Generalization 传递闭包
     - 同一无序对去重: 保留 TYPE_EDGE_PRIORITY 最高类型
  ② LLM 蕴含验证 (批量, 低温度, 高阈值):
     - "A 依赖 B" + "B 包含 C" → 候选 "A 依赖 C" (仅当置信度 >0.85)
  ③ 方向规范化:
     - 双向边 → 按类型语义保留单向 (DIRECTIONAL 集合)
  ④ 置信度标注: 每条关系带 confidence 字段, 前端可过滤
```

**关键点（红线）**：隐含推理的收益必须**以精度为前提**。历史教训（`_connect_global_orphans` 移除）证明虚假关系对 KG 质量伤害大于缺失。所有推理产生的关系必须带 `inferred: true` 标记，可一键过滤/回滚。

#### 预期收益

| 指标 | 当前 | 目标 | 依据 |
|------|------|------|------|
| 关系/实体密度 | 4.6 | <3.5 | 去重+方向规范化 |
| 语义关系覆盖率 | 未测 | +10% | 闭包+蕴含 |

#### 验证方式
- 抽样 100 条推理关系人工评估精确率
- 前端区分显式/推理关系渲染

### 7.5 方向五：多模态输入处理

| 能力 | 现状 | 缺口 |

- 运维场景（本项目目标场景）核心数据形态是**监控指标 + 软件日志**，均非文档文本

#### 落地方案

```

  ① 表格: 行×列 → AttributeDef 属性对 (表头→属性名, 单元格→值)
```

**关键点**：多模态不是"多一个输入格式"，而是**不同数据形态映射到不同实体类型**——SysML v2 本体天然支持（ItemDef 实例、AttributeDef 属性、Trace/Derive 时序关系）。

### 7.6 方向六：跨数据集 GT 比对分析

#### 现状

| 数据集 | 类型数 | GT 实体 | Nanite F1 | 排名 | 特征 |
|--------|:---:|:---:|:---:|:---:|------|
| CLUENER | 10 | 2181 | **0.598** | 🥇 | 新闻/百科，类型粒度细 |
| MSRA | 3 | 2030 | 0.452 | 🥈 | 新闻，仅 PER/ORG/LOC |
| RESUME | 8 | 889 | 0.490 | 🥈 | 简历，领域专精 |

#### 关键分析

1. **类型粒度与 F1 的关系**：CLUENER 类型最多（10 类）反而 F1 最高——说明 Nanite 的提取对类型细分不敏感，短板不在分类而在**召回覆盖**
2. **MSRA vs KGGen**：KGGen R=0.548 领先 Nanite 0.450——KGGen 分块逐块提取更细粒度，Nanite 每 5 段合并 1 次调用，上下文混合导致实体丢失
3. **RESUME vs RAKG**：RAKG P=0.857 领先 Nanite 0.732——RAKG 是逐句 NER（专精 prompt），Nanite 通用提取 prompt 在结构化简历上过度发散
4. **GT 结构差异**：MSRA 的 GT 只标 3 类，Nanite 提取出更多类型时被记为 FP——**类型约束（方向一）直接受益于此**

#### 落地方案

```
① 类型级混淆矩阵: 对 3 个 GT 分别输出 (预测类型 × 真实类型) 矩阵
   → 定位 Nanite 的 type confusion 热点
② 按 GT 结构自适应 prompt:
   - 已知 GT 类型枚举时 → 提取 prompt 内嵌类型列表 (与方向一协同)
   - 未知时 → 保持开放提取 + 事后类型映射
③ 嵌套实体评估: CLUENER/RESUME 有嵌套标注, 评估 Nanite 对嵌套的处理
④ 跨数据集迁移实验: 同一 prompt 在 3 数据集的表现差异 → 判断 prompt 特化 vs 通用
```

#### 预期收益

| 产出 | 用途 |
|------|------|
| 类型级 F1 热力图 | 指导 prompt 特化 |
| prompt 通用性曲线 | 判断是否值得为每个数据集维护独立 prompt |
| 嵌套实体报告 | 量化标注粒度对 F1 的影响 |

#### 验证方式
- 混淆矩阵输出作为报告附录
- 特化 prompt 前后 F1 对比

### 7.7 优化路线图与验证标准

```
Phase P0 (1-2 周) — 快速收益，纯管线改进
  ├─ 7.1 本体约束 (JSON Schema 强约束 LLM 输出)
  ├─ 7.2 实体消歧 (embedding 聚类 + 缩写映射)
  └─ 验收: 同数据集重跑, 精度 +5pp 或 FP -20%; 孤立实体 <5%

Phase P1 (2-4 周) — 能力增强
  ├─ 7.3 领域 RAG (向量传播 + 术语表注入)
  ├─ 7.4 隐含推理 (规则闭包 + 低温度蕴含验证)
  └─ 验收: 召回 +5pp; 推理关系人工抽样精确率 >70%

Phase P2 (1-2 月) — 场景扩展
  ├─ 7.5 多模态 (表格/图表/指标/日志)
  ├─ 7.6 GT 深度分析 (混淆矩阵 + prompt 特化实验)
  └─ 验收: 多模态样例端到端跑通; 类型级分析报告产出
```

**每个方向的共同验收原则**（遵循 AGENTS.md 证据标准）：
- 修改前先定义可观测指标（FP/FN/孤立实体数等），不可用"没崩"当通过
- 修改后用**同一数据集、同一模型、同一 seed** 重跑对比
- 涉及 LLM 的改动必须验证测试场景真正触发了被修改的代码路径（计数器/日志佐证）
